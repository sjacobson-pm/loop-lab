Discovery spec · Persistence model + API contract

Data Schema

Two shapes, not one: persistence (server-side entities the database holds) and API contract (DTOs and operations the client speaks to). The React Application vocabulary is explicit that these must not be conflated.
Starting point. Types, keys, and constraints are proposed — the developer refines against real EF Core migrations. Column descriptions and rule references cross-link with the Rules tab; treat both as authoritative on the same rule.
No sensitivity story
Nothing in this schema is classified. There is no PII, no per-user column, and no field that a second user would be forbidden from seeing (because there is no second user). The interesting risk here is not confidentiality — it is availability of the End of Day summary during the destroy-then-return window; see Workflows for the mitigation. If auth is ever added to this app, every table needs a userId column and every read query needs a WHERE userId = ...; that is a schema migration, not a config change.

Implementation notes

  • Singleton Settings can be enforced at insert time (constant primary key = 1) but there is no clean DB constraint that prevents a second row; the API is the guard.
  • One in-progress DaySession at a time: no natural unique constraint. Enforce in the API: reject POST /api/days if one exists with finalized=false, or auto-return the existing one.
  • Cascade deletes on Template → TemplateItem and DaySession → Timer keep the tables consistent. EoD finalization deletes today's Timers explicitly; DaySession itself stays (with finalized=true and lastSummary populated) for idempotency.
  • Color and icon allowlist: enforce server-side against fixed enums. Do not accept arbitrary strings.
  • Nothing here has a userId column. Adding auth later requires a migration on every table plus a WHERE clause on every read.
  • Aggregate-only: no Events table, no timestamps beyond createdAt/updatedAt. If timeline reconstruction ever becomes a requirement, the schema needs an Events table added; existing tables are not sufficient.

Discovery spec · Constraints and rules

Constraints and Rules

Business logic in draft form. Grouped by screen. Every rule that touches data names the authoritative layer.
Starting point. Formulas below are draft: valid pseudocode in the bound dialects (JS/TS for React, C# for the API), but the developer refines them against the real components and controllers. Some depend on names that do not yet exist.
Where each rule lives. The API is authoritative for every business rule; the React client is a convenience copy that provides immediate feedback and prevents impossible states from being sent. The database enforces the two invariants that must never be violated: unique Template.name, and unique (dayId, workdayCode) per Timer. Nothing else is DB-enforced. This split follows the vocab/react-csharp-stack guidance.

Main Timer view

Only one timer running at a time required

Control: timerCard.startBtn and card click. Property: Timer.isRunning.

The active timer is defined by isRunning: true; at most one may hold that state within a DaySession. Enforced at both layers because the client can hide it but only the API can guarantee it.

Client (React / TS)
function startTimer(id: string) {
  if (settings.autoStartOnSelect) {
    timers.filter(t => t.isRunning && t.id !== id).forEach(pauseTimer);
  }
  patchTimer(id, { isRunning: true });
}
Server (C#) — PATCH /api/timers/{id}
if (patch.IsRunning == true) {
  var another = db.Timers.Any(t => t.DayId == day.Id
      && t.Id != id && t.IsRunning);
  if (another) return Conflict(new { message = "Another timer is already running." });
}

No duplicate Workday code within a single day required

Control: addTimerBtn and editTimerDialog. Property: Timer.workdayCode.

Two timers with the same code would silently split time across identical rows on the summary. Prevented at every layer.

Client (React / TS)
const clash = timers.some(t => t.workdayCode === input.workdayCode && t.id !== editingId);
if (clash) showFieldError('workdayCode', 'That code is already on a timer today.');
Server (C#) — POST /api/timers, PATCH /api/timers/{id}
var conflict = db.Timers.Any(t => t.DayId == day.Id
    && t.WorkdayCode == dto.WorkdayCode && t.Id != id);
if (conflict) return Conflict(new { field = "workdayCode", message = "In use today." });
Database (EF Core / migration)
modelBuilder.Entity<Timer>()
  .HasIndex(t => new { t.DayId, t.WorkdayCode })
  .IsUnique();

Pomodoro elapse notification

Modal fires at every Pomodoro slot boundary required

Control: elapseModal. Property: open state.

Every time the active timer's elapsed count crosses a multiple of the configured slot length, the modal opens. Rearming a timer (via edit) that already crossed a boundary does not re-fire.

Client (React / TS) — inside the tick loop
const slot = settings.pomodoroLengthMinutes * 60;
if (prevElapsed % slot !== 0 && Math.floor(elapsed / slot) > Math.floor(prevElapsed / slot)) {
  openElapseModal(activeTimer);
}

Auto-pause depends on setting required

Control: elapseModal open sequence. Property: Settings.autoPauseOnNotification.

The autoPauseOnNotification setting decides whether the elapse itself pauses the timer. The modal is opened either way.

Client (React / TS)
if (settings.autoPauseOnNotification) pauseTimer(activeTimer.id);
openElapseModal(activeTimer);

Settings.theme is one of 'light' | 'dark' required

Control: btnThemeToggle (header) and toggleTheme (Settings screen). Property: Settings.theme.

Two entry points, one value. Toggling in either place updates the same Settings row. Optimistic UI: client swaps the class immediately and updates the localStorage cache; PUT sends in the background. On PUT failure the class reverts and a toast surfaces the error.

Client (React / TS) — toggle handler
function toggleTheme() {
  const next = settings.theme === 'dark' ? 'light' : 'dark';
  // Optimistic

End of Day summary

Rounding: ceiling, stay on boundary required

Control: summary rows. Property: SummaryRowDto.roundedMinutes.

A code with 15 min of actual time records as 15 min; a code with 16 min records as 30 min. Server authoritative.

Server (C#) — on finalize
static int RoundCeilingStay(double actualMinutes, int increment) {
  if (increment <= 0) throw new ArgumentException();
  var q = actualMinutes / increment;
  var floor = (int)Math.Floor(q);
  return actualMinutes - (floor * increment) < 1e-9
    ? floor * increment                    // already on boundary
    : (floor + 1) * increment;             // bump up
}

Edge cases and follow-ups worth naming

  • Editing a timer that is currently running is allowed; the running state does not change, only the fields being edited. Duplicate-code check runs against all other timers regardless of running state.
  • Changing rounding-increment mid-day applies immediately when the summary is computed. There is no as-of snapshot; the setting active at finalize time is the one used.
  • Deleting a template that was used to seed today's list does not affect today's timers — the seed is a copy, not a live reference.
  • Applying a template that contains a code already on a template is prevented at authoring time (see the "no duplicate workdayCode within one template" rule). A template can never seed a duplicate.
  • OS-level notifications for unfocused tab are a called-out developer follow-up: the Browser Notifications API would let the app alert users when the tab is backgrounded, escalating beyond the in-browser modal. Not in the base spec.
  • Copy all clipboard fallback: navigator.clipboard.writeText requires a secure context (HTTPS or localhost). If unavailable (e.g. HTTP intranet), fall back to a textarea + execCommand('copy'), or show the text for manual copy. Developer to test against the Workday paste target.
Discovery spec · Automations

Workflows

The automations the app depends on. Nothing in this app is a classic long-running background job; the three below cover the tick loop, day finalization, and the optional template save.
Starting point. Every automation carries a mandatory failure section per the workflow slot spec; a happy-path diagram would tell you nothing you cannot read in the steps.

1. Timer tick and elapse detection

Advance the active timer's elapsed count in real time and fire the Pomodoro elapse modal at the slot boundary.
TriggerUser starts a timer, or switches to a paused timer when autoStartOnSelect is on.
Actors / systemsReact client (interval loop, UI state). C# API (persists elapsedSeconds periodically). Local database. Nothing external.
Runs onClient. The API is not driving the tick, it is only accepting periodic updates.
1
Client starts a local interval loop, one tick per second. Each tick increments a local elapsedSeconds counter for the active timer.
2
Every 10 seconds (or immediately on pause or switch), send PATCH /api/timers/:id with the current elapsedSeconds. Server overwrites its stored value.
3
On each tick, check whether elapsedSeconds just crossed a multiple of pomodoroLengthMinutes * 60. If yes, fire the elapse modal.
Branch on autoPauseOnNotification. If true: pause the timer before the modal opens (stop the interval, send final PATCH). If false: keep counting; the user's Take-a-break click pauses it.
4
User picks Take a break (pause, close modal) or Keep going (dismiss modal, continue counting).

What happens when this fails

Tab inactive / backgrounded
Modern browsers throttle setInterval to a minimum of one second in background tabs, and may throttle further after long inactivity. For 25-minute slots this is acceptable: elapse fires within a second or two of the true boundary. Not a bug worth engineering around.
Browser closed mid-day
Server retains last-known elapsedSeconds. On next open, client fetches state and resumes from there. Time during the closed window is not counted, which is the correct behavior (the user was not working).
PATCH fails once
Client keeps counting locally, retries on next 10-second tick. No warning.
PATCH fails repeatedly (network partition, server down)
After N consecutive failures (suggest 3), client surfaces a persistent inline banner: "Not syncing to server. Your elapsed time is only saved in this browser tab right now." User keeps working; on recovery, client sends the final value.
Clock skew between client and server
The tick is driven by client time; server just stores whatever the client sends. Not affected by skew. (Contrast with a server-side ticker, which would be.)
Who finds out
The user, via the banner above. Nobody else; there is no ops channel.
State left behind on failure
Server has an out-of-date elapsedSeconds for the active timer; client has the current one. On successful reconnect, client's value wins.
Safe to re-run
N/A (continuous). PATCH itself is idempotent (last-write-wins on elapsedSeconds).
What this deliberately does not do: fire an OS-level notification when the tab is unfocused (the Browser Notifications API is a called-out follow-up, not base spec). It also does not attempt to reconcile drift between client-side interval and wall clock (e.g. Date.now() correction), which would matter only for hour-plus slots.

2. End of Day finalization

Produce the summary DTO the user copies into Workday, then clear today's Timers server-side.
TriggerUser clicks End of Day, reviews the summary, clicks Finish day, and confirms the modal.
Actors / systemsReact client (confirm gate). C# API (compute summary, destroy timers). Local database. Nothing external.
Runs onServer (compute + destroy). Client only kicks it off and displays the result.
1
Client pauses the active timer (if any) and sends the final PATCH /api/timers/:id so the elapsed value is current on the server.
2
Client calls POST /api/days/current/finalize. No body.
3
Server reads all Timers for the current DaySession, ordered by elapsedSeconds descending.
4
For each Timer, compute roundedMinutes: ceiling of actual minutes divided by roundingIncrementMinutes, multiplied back — with a stay-on-boundary special case (values already on the boundary do not jump up). See the Rules tab for the exact expression.
5
Apply the drop threshold: mark each Timer whose actual minutes are below dropThresholdMinutes as isDropped: true. Do not remove them from the DTO; the client displays dropped rows greyed with a label.
6
Server returns SummaryDto { rows: [...], totalActualMinutes, totalRoundedMinutes, dayDate }.
7
Server destroys today's Timers and marks DaySession as finalized: true in the same transaction as returning the DTO. History is discarded per the design decision (see Scope › Key Decisions).
8
Client renders the summary; user copies rows into Workday and optionally saves a template (Workflow 3). Closing or navigating away leaves the summary until next visit — but the server has already destroyed the timers.

What happens when this fails

Server error during compute (step 4 or 5)
Idempotent so far — Timers not yet destroyed. Client shows error; user retries.
Server error between compute and destroy (steps 6, 7)
This is the dangerous window. Recommended mitigation: persist the last SummaryDto server-side under the DaySession record, so a retry returns the same summary rather than 404. Without that mitigation, a lost response means the user's data is gone and their summary with it.
Client sends finalize but never receives response
Client retries. With the mitigation above, second call returns the persisted summary. Without it, second call returns 409 already finalized and the summary is lost forever.
User cancels the confirm modal
No server call, no state change. Timers continue as before.
User closes the tab after the summary renders but before copying
Timers already destroyed server-side. Persisted summary (if implemented per the mitigation above) is the only recovery path.
Who finds out
The user, when they cannot see their summary. Nobody else.
State left behind on failure
Depends on failure point. Before step 7 — consistent. After step 7 — Timers gone; summary either persisted or lost depending on mitigation.
Safe to re-run
Yes, with the persisted-summary mitigation. Without it, retry after step 7 loses the summary.
What this deliberately does not do: push the summary to Workday's API. Email a copy. Retain the summary past next-day boundary. Log the summary anywhere queryable. All out-of-scope by design; see Scope tab.

3. Save today's codes as a new template

Optional side-flow inside the End of Day summary; captures the day's Workday-code roster as a named Template for reuse.
TriggerUser clicks Save as new template on the End of Day summary.
Actors / systemsReact client (prompt dialog). C# API (validate + create). Local database.
Runs onServer. Client just collects the name and shows the outcome.
1
Prompt asks the user for a template name.
2
Client sends POST /api/templates with the name and the full list of the day's {workdayCode, timerName, color, icon} rows — including any that were dropped (the drop threshold is about the summary, not the roster).
3
Server validates: unique template name (DB constraint), and no duplicate workdayCode within the items.
Branch on duplicate name. Yes: server returns 409; client keeps the dialog open, preserves the entered name, shows inline error "A template named X already exists." No: continue.
4
Server creates the Template + TemplateItems in one transaction; returns 201 with the created Template.
5
Client dismisses the dialog, shows a toast "Template saved." User remains on the summary.

What happens when this fails

Duplicate template name (409)
Client keeps dialog open, preserves data, shows inline error. User re-enters a different name.
Server error (500)
Client shows toast "Could not save template. Try again." Dialog stays open with data intact.
Client sends but never receives response
Retry is safe as long as name uniqueness is enforced at DB level. First successful call wins; second call gets a 409.
Who finds out
The user, in the dialog.
State left behind on failure
Nothing partial — server creates Template + TemplateItems in one transaction.
Safe to re-run
Yes, subject to the uniqueness constraint doing its job.
What this deliberately does not do: filter dropped rows out of the template (all codes go in). Ask the user to confirm each row. Merge into an existing template of the same name (409 forces rename). Update Settings or fire any other side effect.

Discovery spec · Access model

Roles and Personas

Who uses this and what they are allowed to do. Constraint expressions live in the Rules tab; this tab defines the model behind them.
Starting point. The permission matrix is trivial here (one persona, no auth) and that is the design; see the weak-point callout below for what to trade if the app ever grows past a single user.
Single-user by design
Backend option (ii) means no accounts, no login, and no per-user data segregation. There is exactly one persona and one implicit identity on the server. That is not a limitation to work around later, it is what the BA asked for. If the app is ever handed to a second user, the whole access model has to be revisited before that happens; see Model weak point below.

The Timekeeper

The only user. Runs their day against Workday billable codes.
What they are trying to get done
Track how much time they spend on each Workday code across a day, so at end of day they can enter accurate rounded times into Workday's timesheet in one motion. In their own words, per the grill: "input those times and codes into their Workday timesheet."
How often they touch it
Daily, all day. Continuously in the background: start a timer, switch to another when work switches, respond to elapse notifications, add codes ad-hoc, finish the day. This is a get-out-of-my-way daily driver, not a twice-a-year form. The design should optimize for speed of switching, not for onboarding an occasional visitor.
What they can do
Everything. Create and edit timers, apply and manage templates, change global settings, finalize a day. See the matrix below.
What they cannot do
Delete timers. Edit rounded times on the End of Day summary. Both are deliberate; see the Scope ledger.
Which screens they actually touch
All six, but with different weight: Main is the entire workday; Elapse notification is a moment every 25 min; End of Day summary is once a day; Templates and Settings are occasional setup screens.
Abandonment condition
If click-to-switch feels laggy or the elapse modal interrupts more than it helps, this closes and stays closed. Friction, not missing features, is the reason people stop using timekeeping tools. The critical interaction is not any single button; it is the sub-100 ms transition between one code being hot and another being hot.
Model weak point. With no auth, the browser session is the trust boundary. Anyone with local access to the app sees every Workday code, every template, and every day's summary before EoD is finalized. This is acceptable for a single-user tool on the user's own machine, and it is the whole reason option (ii) was chosen over (iii). Do not ship this as-is to a shared host, and do not add a second user without first designing the accounts model that is deliberately not in this spec.
