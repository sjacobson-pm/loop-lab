# US-003 — Settings duration values validate against their spec bounds

## Intent

The Settings screen needs a single shared way to decide whether an entered
duration is acceptable before anything is saved. This story delivers those
rules and nothing else. No input, no form, no persistence.

## Criteria

Cited by anchor. Do not restate.

- `spec/pomodoro-workday-timers-spec.html#rule-pomo-positive`
- `spec/pomodoro-workday-timers-spec.html#rule-rounding-positive`
- `spec/pomodoro-workday-timers-spec.html#rule-drop-nonnegative`

## Acceptance criteria

The one place criteria text may appear, because these describe the shape of
the delivered artifact rather than the behaviour under test.

- A module `src/settings/settingsRules.js` exports one named validator per
  criterion above, each taking the entered value and returning a result that
  distinguishes accepted from rejected. Each validator is named for the field
  the spec names in that rule's detail: `pomodoroLengthMinutes`,
  `roundingIncrementMinutes`, `dropThresholdMinutes`.
- Unit tests are colocated at `src/settings/settingsRules.test.js`.
- Every criterion above has at least one test that fails against the base
  commit and passes after implementation.
- No file outside `src/settings/` changes.

## Out of scope

- Any React component, input, label, or unit annotation. The three control
  anchors are not cited here and belong to the follow-on story.
- Blur handling, focus retention, and inline error rendering
  (`settings-note-invalid`). That is behaviour of a field component that does
  not exist yet.
- Persistence and the save toast. This story ends at a verdict on a value;
  nothing is stored.
- The two boolean toggles, which have no validation semantics.
- Theme, which carries a server-persistence decision no web-only vertical can
  satisfy.
- The mid-day-change note, which depends on timer mechanics.
- Server-side enforcement. `rule-pomo-positive` states both the bound and that
  the server refuses a violating PUT with 400. This story satisfies the bound
  only. There is no API in this repo, so the 400 is a second enforcement point
  belonging to the api stack, and no task may be generated for it.
- Any constraint the spec does not state. The rules bound sign and nothing
  else — no integer, step, or upper bound is specified, so none is implemented.

## Notes

`PROJECT.md` is advisory context only and may not be cited as a criterion.

The spec is HTML, not markdown. Anchors above resolve against `id` attributes
on the tagged elements; the semantic ids also appear as `data-pd-*` attributes
on the same elements.

This story is the first executable carve of US-S04 in the settings slice. The
remaining US-S04 anchors — the three controls and `settings-note-invalid` —
are unplanned, not dropped.
